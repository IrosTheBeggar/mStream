Downloads tab — the scratch library and its clock

Get it plug-ins land files in Discover downloads, a real library (discover-downloads) created on the first download, one subfolder per user. A file stays until its owner presses Keep… (it moves into their collection) or it turns discoveryJobs.downloads.retentionDays old and the retention pass removes it. Retention is a clock, not a quota, so the folder also has a size cap (maxSizeMb, 5 GB by default): at the cap, new downloads are refused until something is kept, removed or expires. This tab is where the operator watches the disk and sets both. Copies from a paired server never come here: they go straight into the user’s library.

Rules

Numbers come from one route: GET /api/v1/admin/discovery-plugins/status → downloads { dir, exists, retentionDays, files, bytes, partials, freeBytes, oldestAt, newestAt, byUser[], sweeping, lastSweep { at, removedFiles, removedPartials, skipped, prunedJobs }, nextSweepAt }. It reads the folder itself (size and mtime), the way the pass does, and stops counting at 5,000 files; half-written files are counted apart, never as downloads. freeBytes is one statfs and is null where the runtime cannot say (the tile then drops its grey line).

The User column is the account’s subfolder (its username made path-safe; shared on a server with no users). The file’s age is its mtime, the same clock the pass uses, so “4 days left” here and “removed in 4 days” in the user’s window agree.

The admin does not delete individual files here. They are library songs: the file explorer and the library already do that. The panel owns the clock and the one button.

The clock and the cap are two keys on the existing setter: POST /api/v1/admin/config/discovery-jobs { downloadsRetentionDays, downloadsMaxSizeMb }. The cap’s [edit] takes gigabytes (decimals allowed) and saves megabytes; the status answer carries maxSizeMb and full. Half-written files count against the cap.
