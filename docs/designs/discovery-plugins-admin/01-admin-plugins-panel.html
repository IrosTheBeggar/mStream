Discovery Plugins — the admin view

A new view in the admin panel, next to Discovery. It answers one question for the operator: what can people on this server do with a recommendation, and who is allowed to? Everything on it is live — no restart, no APPLY button — because the registry and the job gate read the config per request.

Callouts

  1. 1Nav entry “Discovery Plugins” under Config, directly below Discovery, in the same cyan. Stroke plug icon. View id discovery-plugins-view. Measured in the running admin: the label fits the 200 px sidebar on one line with 3 px to spare.
  2. 2Status header, the Discovery view’s boxed header: a dot and one sentence (how many plug-ins are on, how many cannot run, who may start jobs, what is running now), and [Refresh].
  3. 3Four tabs as the Discovery view’s pills. Activity carries a count while jobs run. The tab is session-local; a page load lands on Plug-ins.
  4. 4Groups are the window’s sections, in the window’s order (Listen, Get it, Send to, Find elsewhere), so the operator sees which row each switch adds. A group with no plug-in installed is not drawn.
  5. 5A plug-in row: switch · title, capability tag, scope tag · one-line description · status and bracket links on the right. The switch applies at once and toasts.
  6. 6Cannot run: the plug-in is on but its availability probe fails. The row says why in the probe’s own words and offers [settings] and [check again]. Users never see this row in the window; only the admin does.
  7. 7Scope tag per user marks plug-ins that act with the user’s own rights or credentials (copies need upload rights; ListenBrainz will need each user’s token).

Why tabs, not stacked cards

The four concerns are used at different moments (set up · decide access · watch the disk · answer “my download failed”). Tabs keep each one a screen tall and match the sibling Discovery view; Torrent-style stacked cards would run past 2,000 px.
