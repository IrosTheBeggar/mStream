# Discovery page — plan

Status: plan v2, 2026-10-05, after an adversarial review (3 lenses + synthesis; every finding below was verified in code). Design canvas: https://claude.ai/artifact/SgZVPShtC92MFhkrkJbLcA (visuals; §2.13 lists where this plan deliberately differs).
Facts were verified against mStream `926b97b1`, `mstream_music` master `bdb174e0`, `mstream-terminal-player` origin/main `2b04dbe` (v0.12.1).

## 1. What we are building

A **Discover page** on every client (webapp, mobile app, terminal player in GUI mode only) seeded by the user's **play history** instead of the now-playing song, showing three sources:

| Source | What it holds | Verbs on a row |
|---|---|---|
| **Library** | songs and albums in the user's own libraries that sound like the seeds and that you **haven't played lately** (never played, or not in 90 days) | inline play / queue / queue next + the existing track-actions ⋯ |
| **Network** | p2p discovery leads the library does not own | the row opens the existing recommendation window (webapp) / sheet (mobile, phase B) / anchored menu (terminal); the discovery **plug-ins** the server has on decide the verbs: 30 s preview, Get it (YouTube job), Open elsewhere, lookup |
| **Peers** | songs on federated servers the library does not own, playable through this server | inline Listen and queue (federation stream proxy, never a plug-in) + a peer-row ⋯: **Keep a copy** (federation-copy job when the plug-in is on, `jobs.allowed`, upload right), Browse this server, Open elsewhere |

Seeds = a **random batch** of the distinct songs the user **finished or mostly listened to** recently — a new batch every time the page opens. Skipped plays never seed.

Row verbs per source are the same on all clients: Library = inline play/queue/next + track-actions ⋯; Network = the row opens its window/sheet/menu, no inline verbs; Peers = inline Listen/queue + a peer ⋯ that is NOT track-actions (no rate / playlist / go-to-album for a peer path). v1 on mobile and terminal: Network rows carry no plug-in verbs (§4.2, §4.3 phasing).

## 2. Decisions (product assumptions — chosen, flagged)

1. **Seed rule**: from `play_events` through `whereEvents` + `eventScope(user, ignoreVPaths)` (the stats routes' library scope): `track_hash IS NOT NULL AND peer_id IS NULL AND counted = 1 AND (outcome = 'completed' OR (outcome = 'stopped' AND played_ms >= 0.5 * duration_ms))`, within the window, `GROUP BY track_hash`, and the hash's latest event in the window must not be a skip. Every candidate in the window is read (the GROUP BY and the skip check visit every group anyway), then a **random batch** is drawn: a lazy Fisher–Yates shuffle takes candidates one at a time, keeping only hashes present in `index.byHash` **and** returned by `resolveVisible` for this caller, until `limit.seeds` — uniform over the accepted candidates, not newest-first, so every call (every page open) seeds from another set. The SQL reads the whole window (no extra query time: the GROUP BY visits every group anyway), but each drawn hash that passes the index check costs one `resolveVisible` probe, so a call stops probing after 96 failed probes (`VISIBLE_MISS_CAP` = 2 × 12 × 4, the bound the old newest-first pages had) — a history mostly of songs since deleted then falls through to the random seed instead of probing every song ever played. The seeds come back pins first, then in draw order. Each seed carries `outcome` so copy can say "finished" vs "listened to". (`counted = 1` is required because a seek to the end classifies as completed; a tab closed 35 s into a 6-minute song is stopped and under 50 %, so it does not seed.)
2. **Window**: 7 · 30 · 90 days · all time; default 30. Widening order when the window yields nothing: window → all-time events → `user_metadata` counters (`play_count > 0 ORDER BY last_played DESC`, resolved through `resolveTracks`/`resolveVisible`) → random. The response reports `seedSource: 'history' | 'counters' | 'random' | 'pinned'` and `widenedFrom` (the requested window when widening happened). Counters are skipped when the log is empty because of `POST /stats/reset` (not retention): a reset of `history`/`all` stamps a `resetAt` marker in `user_settings` namespace `discovery:page` (the only thing the page stores per user) and counters last bumped before it do not seed.
3. **Pins**: the client may pass `pin: [filePath]` (≤ 12 = the seed cap, so a client can pin a whole seed batch; now playing first, songs the user picked). Pins are explicit choices, so they seed regardless of history (and override an exclusion); they last for the visit only (not persisted). Pinning happens at page open or via an explicit "+ Now playing" chip — never a refetch on track change (a "seeds changed · refresh" affordance instead). `exclude: [hash]` (cap 200) leaves songs out of **this call's** pool — nothing is remembered between calls; an excluded song is also never recommended back in the library section, like a seed, and the answer lists the excluded rows (`excluded`) so a client can offer them back within the visit.
4. **Ranking**: one taste vector = `sim.centroidOf(seedVecs)` for the network and peer fan-outs (the federation responder takes exactly one vector; p2p is one pass per peer matrix). For the library, a per-seed pass with max-similarity merge so each row can say *because you finished X* (`seedHash` on the row). Cost is linear in seeds (~24 ms/seed at 25k×1280 on M-series; a fused multi-accumulator loop measured slower), so the library pass uses at most **6 history seeds + pins** (pins count toward `limit.seeds`), yields to the event loop between passes (`await new Promise(setImmediate)`), and reuses one score buffer. Every call computes its answer (no result cache — with a new seed batch per call a cache would rarely hit); clients fetch on open or on a tap and never poll.
5. **Library rule (fixed)**: "songs you haven't played lately" = `play_count` null/0 **or** `last_played < now − 90 days` (`DEFAULT_STALE_DAYS`; no request can change it, and there is no other filter). `trackQuery` gains `um.skip_count` (S0) so rows carry it; tracks with `skip_count > 0 AND play_count = 0` ("tried and bounced") and tracks rated 2 stars or less (`rating ≤ 4` on the 0–10 scale) are excluded too. Library candidates whose `entry.nameKey` equals any seed's nameKey, or whose similarity to their own seed is ≥ `NEAR_DUP` (0.99), are dropped (re-encodes and alternate files of the seed song read as unplayed otherwise); accepted rows are deduped by nameKey (best file kept). Each row carries `playCount` and `lastPlayed` (ISO via `toIso`) so clients label "never played" / "last played 8 months ago". Cutoffs are built with `toSqlite()`.
6. **Albums before songs** in the library source. Candidates come from the whole ranked walk (the `considerBudget` pool, not only the accepted top-N), keyed by the Album card identity `(name, year, album_art_file)` that `/db/albums` uses, ranked by the max similarity of their tracks. One batched query computes per card `scopedTracks` (tracks in the caller's libraries), `playedTracks` (LEFT JOIN `user_metadata` on the `(user_id, track_hash)` probe, `play_count > 0`) and `lastPlayed`. `track_count` keeps its existing all-libraries meaning. "Unplayed album" = `playedTracks = 0`; an album also qualifies when `lastPlayed < cutoff` (the same 90 days). Songs listed inside a returned album are left out of `library.tracks`.
7. **Network = p2p only, peers = federation only**; novelty/owned checks run caller-side as today. The taste route **stamps `source: 'p2p'`** on every network row and **`source: 'federation'`** (plus `peer`, peer-side `filepath`) on every peers row, so every row is a ready-to-send recommendation that clients forward unchanged to resolve/jobs/lookup (`stripUnknown` makes extras like `seedHash` harmless). Network rows get `seedHash` from dots of the final top-N against each seed vector (cheap) and are deduped by `recommendationKey` across peers; federation rows get `seedHash: null`.
8. **Nothing to seed from** (no counted plays at all, after widening): `seedSource: 'random'`, one analyzed track **from the caller's own libraries** (via `resolveVisible`, drawn fresh on every call — `exclude` keeps a song out, so a client's "Another pick" re-asks with the picks it showed this visit), `fallback: true`. Network and peers fan-outs are skipped for a random seed; clients draw the "finish a few songs" card with a "Start from a song…" pin action. Discovery off → 403 (house convention); scan pending → `notAnalyzed: true` with the seeds listed.
9. **Placement**: webapp — a `Discover` side-nav entry in the **Music** group after *Most Played* (it is a browse destination like Recently/Most Played; the System group holds tools); mobile — a per-server **home card** under *Listen* beside Auto DJ / Sonic path (taste is one server account's history; the drawer is for cross-server things); terminal GUI — a **TOOLS nav room** `Discover` under Sonic path at row 16 (TOOLS label moves to the gap row 13; Settings stays on the content's last row, 17 at 100×24), gated on the flags, hidden in peer sessions.
10. **Flag, never probe**: a new `features.discoveryTaste: 1` (an integer generation like `stats: 2`; a later body key ships as 2 and needs no client floor entries). It is a version fact, so every client gates the page on `discovery === true && discoveryTaste >= 1` (webapp: ping; mobile: `discoveryAvailable && discoveryTasteAvailable`; terminal: `capabilities.discovery && capabilities.discovery_taste >= 1`). **Ping lists capability keys by hand** (`src/api/playlist.js`), so S5 adds `discoveryTaste: features.discoveryTaste` there; the drift-lock test `test/integration/api-server-info.test.mjs` is the parity check and must stay green. Clients also need to read the already-advertised `discoveryPlugins` (mobile and terminal do not deserialize it yet).
11. **No new plug-in capability.** A recommendation *provider* is not a plug-in in this contract (the registry rejects unknown capabilities); the page is a server-side aggregator over the three existing sources, and plug-ins stay "what you can do with a row".
12. **Naming**: the history-seeded page alone is called **"Discover"**. The per-song lens is retitled **"More like this"** on the webapp (the now-playing panel's `discover.title`) and mobile (`DiscoverScreen` title, queue-bar tooltip, `p2pFindSimilarSub` in all 10 ARBs); the terminal's Now Playing tab becomes **"Similar"** (fits the tab row; keymap help for key 4 and `gui.tips` follow). The P2P screen's "Find similar music in the network" keeps opening the per-song lens. Reversible by the user; strings only.

## 3. Server contract (mStream)

### 3.1 `POST /api/v1/discovery/taste`

Auth: a logged-in account (`requireAccount` rule: 403 for federation keys and guests; the public-mode sentinel passes); the whole `/api/v1/discovery/taste` subtree is prefixed with `refuseJukebox`. 403 `Discovery is disabled` when `collectDiscoveryData` is off or the index is unavailable (`requireIndex`). The route pays a `getIndex()` rebuild like every similar route; clients fetch on every open and on a tap — no client-side TTL or reuse of an earlier answer, since a new random seed batch per open is the expected behaviour (§2.13) — and never poll or auto-fetch on every home render.

Body (Joi, all optional; nothing is stored between calls; an unknown key — including the removed `remember`, `filter`, `staleDays` — is a 400):
```json
{
  "window": 30,                 // 7 | 30 | 90 | 0 (= all time); default 30
  "pin": ["<vpath>/<rel>"],     // ≤ 12 (= limit.seeds' cap); unknown/forbidden paths are dropped silently, counted in `dropped`
  "exclude": ["<hash>"],        // ≤ 200 × Joi.string().max(128); left out of THIS call's seed pool (and of the library results); never stored
  "sources": ["library","network","peers"],
  "limit": { "seeds": 12, "tracks": 24, "albums": 8, "network": 12, "peers": 12 },   // caps 12 / 50 / 24 / 50 / 25-per-peer
  "newArtistsOnly": false,      // client-local pref, passed per call
  "ignoreVPaths": []
}
```

Response:
```json
{
  "window": 30, "widenedFrom": null,
  "seedSource": "history" | "counters" | "random" | "pinned", "fallback": false,
  "seeds": [{ "hash": "…", "filepath": "<vpath>/<rel>", "metadata": { …lite }, "outcome": "completed", "lastPlayed": "2026-10-04T21:10:00.000Z", "plays": 3, "pinned": false, "analyzed": true }],   // pins first, then the random batch in draw order
  "excluded": [{ "hash": "…", "filepath": "…", "metadata": { …lite } }],   // this call's `exclude` hashes that resolve to a visible track, to offer back within the visit
  "dropped": 0, "notAnalyzed": false,
  "model": { "id": "effnet-discogs", "version": "…" },
  "library": {                  // the fixed "not played lately" rule (§2.5); no filter field
    "tracks": [{ "filepath": "…", "similarity": 0.83, "seedHash": "…", "metadata": { …lite }, "genreTags": [...], "playCount": 0, "lastPlayed": null }],
    "albums": [{ …Album shape (track_count = all-libraries count, unchanged), "similarity": 0.84, "seedHash": "…", "scopedTracks": 11, "playedTracks": 0, "lastPlayed": null, "tracks": ["<vpath>/<rel>", …] }],
    "capped": false
  },
  "network": { "results": [ …p2p similar rows + { "source": "p2p", "seedHash": "…" } ], "searched": { "peers": 3, "tracks": 7421 } } | null,
  "peers":   { "peers": [{ "id": 1, "name": "Sam's server", "reachable": true, "mismatched": false, "lastSeen": "…" /* federation_peers, may be stale */, "results": [ …federation rows (incl. "albumArt": "<peer's cover file>" | null, since 2026-10-16) + { "source": "federation", "seedHash": null } ] }], "searched": { "peers": 3, "unreachable": 1, "mismatched": 0 } } | null
}
```
**Peer covers (2026-10-16)**: every peers row carries `albumArt` — the track's cover file name on the PEER, exactly as the peer's own browse rows name it (`metadata['album-art']`, which its `/album-art/<file>` serves), or `null` (no cover, a peer on an older server, or anything from the peer that its `/album-art/` could not serve: the fan-out keeps only names matching that route's own `sanitizeFilename` pattern, `^[a-zA-Z0-9_-]{1,100}\.[a-zA-Z0-9]{1,7}$`, `peerArtName`). The peer's responder (`/api/v1/federation/discovery/similar`) adds the field; A's fan-out (`mergePeerAnswers`) and the taste route pass it through, so the per-song `/discovery/federation/similar` rows carry it too. A client draws it as `<A>/api/v1/federation/peers/<peer.id>/art/${encodeURIComponent(albumArt)}?compress=<s|l>` (the webapp's `peerArtUrl(peerId, art, size)`) — always encoded, even though A only forwards URL-safe names. Sizes: a song row's 40 px tile asks for `s` (the peer's `zs-` file, at most 92 px a side); a connected-server album card uses the first row's `albumArt` in its group and asks for `l` (`zl-`, at most 256 px — what the library's cards use in compressed-art mode), always, whatever that layout setting, so no full-size original crosses the proxy for a 150 px card (2026-10-17). A's art proxy forwards the `compress` query to the peer as is; the peer's own `/album-art/` serves its full-size original when it has no cached variant for that cover (`compressImage` off, no ffmpeg, a cover cached before thumbnails), so the card still draws, just heavier. Null keeps the note tile. Additive: no request change, no flag bump.
`network`/`peers` are `null` when the source is not advertised for this caller (discoveryP2p / federationDiscovery) or when a random seed is in use; when asked and empty — including while no seed is analyzed (`notAnalyzed`) — `network = { results: [], searched }` and `peers = { peers: [], searched }`. No copy permission is returned: "Keep a copy" is gated on the federation-copy plug-in being listed + `jobs.allowed` + the upload right, and a peer's refusal surfaces as the job's error. `reachable` reflects this call's outcome; on success the route calls `updateFederationPeerStatus` (throttled to once per peer per 5 minutes). The federation fan-out is started (unawaited) before the synchronous library and p2p work, then awaited. **Clients SHOULD request `peers` in a separate call** (`sources:['library','network']` + `sources:['peers']`) so the library renders without waiting for a 4 s peer deadline. A peer whose dial failed twice in a row (that deadline missed, or its handshake refused) is not dialed again for 60 s, doubling up to 10 min while it keeps failing, and is reported `reachable: false` at once meanwhile; an answer, or the admin's successful test-connection, resets it (in memory only, `peerFailures` in `discovery-federation.js`; nothing is written to `federation_peers`), and the per-song route's `peerId` always dials (2026-10-17). A failure while the caller's own federation endpoint is down (boot, where it binds after HTTP is serving; a reboot; federation just enabled) does not count: no peer was asked. Since every call draws its own random batch, the peers call goes out once the first answer lands, pinned to that answer's seeds (`pin` = every seed path of that answer — at most 12, `PIN_CAP` = the seed cap — and `limit.seeds` = their count) so the connected-server rows come from the batch the picker shows; a `seedSource: 'random'` answer gets no peers call. Every new timestamp is ISO through `toIso`. Privacy note for the openapi description, the admin `use_discovery` copy and `discovery-federation.js`: the peers fan-out sends every `use_discovery` peer the centroid of the seeds — a random batch of up to 12 songs the caller finished in the chosen window (all time with `window: 0`) plus pins.

### 3.2 ~~`GET /api/v1/discovery/taste/prefs` · `PUT …/prefs`~~ — removed 2026-10-14
The saved page prefs are gone (§2.13): nothing about the page is stored per user except the stats-reset marker (§2.2). The window is sent per call; `newArtistsOnly` stays client-local (webapp localStorage `discoverNewArtistsOnly`, mobile `SettingsManager`).

### 3.3 `POST /api/v1/discovery/plugin-jobs/lookup/batch` — new path
Body `{ recommendations: [rec, …] }` (Joi `.min(1).max(100)`); answers `{ results: [{ key, keys, jobs }, …] }` in input order, from one `jobsDb.latestForKeys` call split back per recommendation by key. Same gates as the single form (refuseJukebox prefix, user-scoped rows). The existing `POST /plugin-jobs/lookup` is untouched (strict Joi; adding a key there would 400 on 6.30/6.31 servers). Clients call the batch path only when `discoveryTaste >= 1` is advertised and fall back to per-row single lookups otherwise.

## 7. Risks
- `getIndex()` rebuilds block the event loop (~1.7 s at 25k) after an epoch change; the route pays it like every similar route. Clients fetch on open/tap (every open refetches) and never poll.
- Library pass ~24 ms per seed at 25k (cap 6 + pins, yield between passes) plus the p2p pass ~370 ms at 6×25k peer rows; no result cache, so every open pays it (clients fetch on open/tap only).
- Federation fan-out is up to 4 s per unreachable peer: started first, awaited last, unreachable peers answered as a group with `reachable: false`; clients ask for peers in a separate call, chained on the first answer's seeds (§3.1). A peer that keeps failing costs that 4 s once per cool-down (60 s, doubling to 10 min), not on every open (§3.1).
- Mobile: the primary checkout is on `feat/windows-desktop`; building from it would lose the play-history files.
- Terminal: the local `main` is 153 commits behind; branch from `origin/main` or the pin bump will not apply.
